# Trasa MVP API decisions

The normative target is [OpenAPI 3.1](../api/openapi.yaml), version 1.1.0. It is deliberately breaking relative to the current implementation. This revision expands authentication for users and administrators and corrects the full contract's resource/error semantics. No backend algorithm, persistence pattern, framework or provider is prescribed.

## Resources and presentation

- IDs are opaque strings, matching existing CUID-style backend IDs. Numeric IDs in the planning examples were illustrative. Category IDs are the stable strings `sightseeing`, `food`, `entertainment`, `nature`; Polish display names come from `/categories`.
- A Place is an independent reusable resource with multiple categories. Available Places are public and eligible for generation even if no curated route references them. Unavailable Places are admin-only; imports start unavailable for review. No category or city administration is needed.
- A route stop is ordered membership with an embedded Place, not a copy with an unrelated identity. Positions are contiguous and one-based. The first stop is the start; no separate starting-point field or stop-details GET is necessary.
- Curated summaries omit stops and geometry. Complete curated routes and generated results share `city`, `title`, `categoryIds`, `statistics`, `stops` and `geometry`. Both use a compact city `{id, name}`; centre coordinates/description remain in cached `/cities`. Stops embed full public Place details, including descriptions, for the existing shared viewer without N+1 requests. Generated results have no permanent ID, status or storage operation. Both route kinds report the actual union of returned Place categories in `/categories` order, including co-tags; this does not claim every requested category was matched.
- Each Place/curated route has one nullable HTTPS `imageUrl`. Omission on a complete write clears it; responses always include null when absent. No media provider, upload system or galleries are required.

## Generation, walking and limits

`POST /route-generator` returns a completed result synchronously. City, one or more categories, per-person whole-PLN budget, maximum total minutes and intensity are required. There is no `mixed`, group budget, unlimited time, persistence, job, history, polling or regeneration endpoint. Repeating a request may return the same result; variation is not an MVP guarantee.

Available candidates must be in the requested city and intersect the selected categories (OR matching). Category coverage is a preference: prefer broader requested-category coverage among equally feasible choices, but a feasible subset is valid. Every returned Place must match at least one requested category. Success still requires at least two distinct Places and must meet **all hard** budget/time/intensity limits. Optional `excludePlaceIds` (up to 50 unique IDs) enables another variant: every exclusion is respected, while unknown/other-city IDs are harmless. If exclusions or limits make a route impossible, return `422 NO_FEASIBLE_ROUTE`. An unsupported request city is `422 CITY_NOT_SUPPORTED`; provider failures remain distinct. No ranking algorithm or guarantee of a different route without exclusions is prescribed.

Intensity has a concrete, inclusive walking-distance ceiling: `low` = 3,000 m, `medium` = 6,000 m, `high` = 10,000 m. Higher intensity permits more walking, but does not promise a longer route or imply accessibility/terrain suitability. These are product defaults chosen for the contract; they are not algorithm instructions.

Statistics are identical across route sources:

| Field | Meaning |
| --- | --- |
| `distanceMeters` | Routed pedestrian distance, rounded up to metres |
| `walkingDurationMinutes` | Routed walking estimate, rounded up to minutes |
| `visitDurationMinutes` | Sum of Place visit minutes |
| `totalDurationMinutes` | Walking plus visits, exactly |
| `estimatedCostPln` | Sum of per-person Place estimates |
| `stopCount` | Length of ordered stop list |

Limits apply to the returned rounded values. No travel to the first stop or from the last stop is included. Prices and times are estimates, not opening-hours or ticket-availability guarantees. Input bounds are 0–100,000 PLN for a route budget, 0–2,000 PLN for one Place, 30–720 total minutes, 0–480 visit minutes, and at most 50 stops. These are finite MVP validation bounds, not additional UI controls.

Walking geometry is a backend-supplied WGS84 GeoJSON `LineString`, in `[longitude, latitude]` order. It follows the pedestrian network through stop access points in sequence. Public/generated routes always include it; a straight connection between POIs is not acceptable. The frontend renders it without deriving walking distances or geometry. Mapbox is the frontend map requirement; REST payloads remain provider-neutral. No leg-time field is included because the MVP requires route totals, not per-leg instructions. Existing per-leg labels must be removed rather than estimated client-side.

Draft geometry/statistics can be null. Stop changes invalidate them together; publication produces valid routing data synchronously. No provider failure creates a partial publication or fake route. Transport examples are illustrative Poznań data, not independently verified walking directions.

## Authentication and administration

Public browsing/generation stays anonymous, even when the client has no valid session. Regular users and administrators share registration/verification/login/refresh/logout/password-change contracts. Only roles `user` and `admin` are exposed; registration cannot accept a role and always creates an unverified regular user. Administrator provisioning remains outside this API; provisioned administrators must also have verified email before login. No MFA, OAuth, role management, device panel or password-reset API is added.

Registration and resend return generic `202 {data:{verificationRequired:true}}` for new/existing/unknown/verified addresses as applicable, without tokens, account IDs or duplicate-email conflicts. Registration never overwrites an existing account or implicitly resends to it. Generic acceptance does not guarantee email delivery; use resend if needed. Code-delivery failures do not expose eligibility/provider details. Shared request limits apply identically to all normalized addresses: one per 60 seconds and five/hour per email, plus 20/hour per IP; excess requests return 429 with Retry-After. Input errors are still 400. Email is trimmed/lowercased; passwords are never transformed. New passwords are 12–128 characters with at least one non-whitespace character, without character-class rules.

Verification uses the latest six-digit one-time code, valid for ten minutes and at most five failed attempts before consumption. Resending invalidates previous codes; successful verification consumes the code. Invalid/expired/used/exhausted codes and unknown emails share `400 INVALID_VERIFICATION_CODE`; verification retries cannot reveal account existence. A separate 10/minute per-IP submission limit returns 429. Verification success grants no session: the next step is login. A correct password on an unverified account returns `403 EMAIL_NOT_VERIFIED`; wrong passwords/unknown/disabled accounts share 401. Login throttles are 10 attempts/15 minutes per normalized email and 30/15 minutes per IP, independent of account existence.

Login creates one refresh session and returns access/refresh tokens, `tokenType: Bearer`, `expiresIn: 900`, and `refreshExpiresAt` (login + seven days). `/user/me` with an access token restores `{id,email,emailVerified,role}`. Only role admin can access `/admin/*`: invalid/expired credentials are 401, authenticated regular users are 403. Refresh tokens never work as access bearer credentials. All auth and `/user/me` responses, including errors, use `Cache-Control: no-store`; HTTPS is mandatory outside development. Keep refresh tokens in native secure device storage and avoid logging credentials. Protect refresh credentials at rest using non-recoverable verifiers where feasible; token encoding/storage internals remain backend choices.

Refresh checks original expiry, revocation and account eligibility, issues a new 15-minute access token and returns the **same refresh token and unchanged absolute expiry**. No rotation or sliding expiration occurs. A refresh failure is 401 without a new session. A last access token can outlive refresh expiry by at most 15 minutes; this never restores refresh validity. Refresh/logout allow 60 requests/minute per IP.

Logout accepts the refresh token without an access bearer, so it works after access expiry. It revokes that refresh session server-side, then returns 204; unknown/expired/already-revoked tokens are successful no-ops. Other login sessions remain valid. Issued access tokens may remain valid until their own expiry (up to 15 minutes); local deletion alone is insufficient. A failed revocation must not return success. Password change requires access bearer plus current/new password; success invalidates **all** account refresh and access tokens immediately, issues none, and requires login again. Incorrect current password is `400 CURRENT_PASSWORD_INVALID`; unchanged/invalid new password is 400 validation error. Password-change attempts are limited to five/15 minutes per authenticated account and 30/15 minutes per IP. This stronger password-change invalidation is deliberately different from ordinary logout.

Curated-route metadata/stops editing and deletion still require an unpublished route. For Places, compare normalized changed values rather than treating every full PUT as a routing edit. Name, description, address, image URL and category changes are safe on published dependencies; update embedded Place data and derived route category unions consistently, retaining valid geometry/statistics. A change to coordinates, availability, estimated cost or visit duration is rejected with `409 PLACE_IN_PUBLISHED_ROUTE` when any published route depends on the Place. Unpublish those routes first; draft-only dependencies invalidate geometry/statistics together. The whole write succeeds or fails; no stale calculated data or complex dependency machinery is required. Place city remains immutable; route city changes require no stops. Public drafts/unavailable Places return 404. Previously generated results are client-held snapshots, so later edits/deletion may make their Place links unavailable without invalidating their historical result data.

`PUT /admin/routes/{routeId}/stops` atomically replaces the full ordered `placeIds` list: selection, removal and reorder share one operation. Duplicate IDs are 400; nonexistent and cross-city references are 422 with indexed field issues. Drafts may be empty or contain unavailable Places, but publication requires at least two distinct available Places and complete descriptions. Removing membership never deletes a Place. Any remaining draft/published reference blocks Place deletion with 409.

External search returns at most 10 nonpersistent candidates for one city. Import uses the returned provider identity, obtains authoritative provider content, and creates an unavailable internal Place. Missing category/description/address can be completed manually; default cost 0 and visit time 30 are review estimates, not provider claims. Missing usable name/coordinates is a provider error, not grounds for fabricated data. Re-import returns the existing Place unchanged (200 versus 201 for creation), without needing another successful provider lookup; cross-city identity conflicts are 409. Backend selects the provider and handles credentials; the client does not call it directly.

## Collections, writes and errors

Every success body is `{ "data": ... }`; deletion/logout/password change use 204 without a body, registration/resend use generic 202. Lists are complete and unpaginated. Only public `/routes` supports a `cityId` filter, because Home and city browsing need it; no category filter, search, sorting control or pagination is exposed. Cities/Places sort by name then ID, routes by title then ID, categories use the fixed order above, and POIs use provider relevance. Empty matches, including syntactically valid unsupported cities on route filtering or POI search, return 200 with `data: []`. POI search skips the provider call for an unsupported city. A missing/hidden path resource is 404; an unsupported city body reference on generation/create/import is `422 CITY_NOT_SUPPORTED`.

PUT replaces complete editable fields; server-owned IDs/status/statistics/geometry/provider metadata are not writable. JSON numbers must be numbers, not strings. Reject unknown body/query fields. Trim display text before checking required lengths. All write failures leave the requested change unapplied. Errors retain `{error:{code,message,issues?}}`, with dotted field paths and `$` for a whole-request issue. Clients branch on codes and translate their own messages. Schema errors are 400, missing resources 404, state conflicts 409, feasibility/readiness/reference failures 422, provider/service failures 502/503. Auth/generation rate limits return 429 with Retry-After. Only relevant errors appear per operation; conflict examples now describe the actual route/Place/city conflict.

Error meanings are operation-scoped: `UNAUTHORIZED` (401) never distinguishes invalid/revoked/expired sessions; `FORBIDDEN` (403) is admin authorization; `EMAIL_NOT_VERIFIED` (403) is only returned after correct credentials. `INVALID_VERIFICATION_CODE` and `CURRENT_PASSWORD_INVALID` are the documented 400 auth failures. `NOT_FOUND` (404) hides unavailable path resources. `CITY_NOT_SUPPORTED`, `PLACE_NOT_FOUND`, `PLACE_CITY_MISMATCH`, `POI_NOT_FOUND`, `ROUTE_NOT_READY`, `NO_FEASIBLE_ROUTE` are distinct 422 cases. Immutable-city/published-route/reference/import conflicts use their named 409 codes. `PROVIDER_ERROR`, `SERVICE_UNAVAILABLE`, `RATE_LIMITED`, `INTERNAL_ERROR` mean 502, 503, 429, 500 respectively; `VALIDATION_ERROR` is 400.

## Frontend compatibility and request mapping

| Current screen/code | Target data and required adaptation |
| --- | --- |
| `client/src/app/(tabs)/index.tsx` | `/cities`, `/categories`, `/routes?cityId=…`; select city by ID, derive Home examples locally; these are not ranked popular routes |
| `client/src/app/(tabs)/explore.tsx`, `app/city/[slug].tsx` | Reuse cached cities and compact route list; drop server search/time/distance/category filters, slug lookup and extra city-details request |
| `client/src/app/route/[slug]/…` | Navigate by stable route ID; one `/routes/{routeId}` response supports details, itinerary and map |
| `client/src/app/plan/…`, `context/plan.tsx` | Fetch categories; submit required per-person budget/time/intensity and optional exclusions; remove `MIXED`, `people` and null/unlimited time; allow category subsets and handle infeasibility separately |
| `components/plan/planned-route.tsx`, `types/itinerary.ts` | Reuse route viewer with server title, shared statistics, embedded `stop.place`, and geometry; no permanent generated ID is needed |
| `components/route-map.tsx`, `route-map.web.tsx`, `lib/itinerary.ts` | Accept independent backend geometry; replace current stop-to-stop lines, stop client walking-time estimates; Mapbox integration remains frontend work |
| `components/itinerary/stop-screen.tsx` | Place identity is `stop.place.id`; independent `/places/{placeId}` screen can use embedded preview and fetch details, without forcing an itinerary N+1 |
| `api/client.ts`, `api/queries.ts`, `types/domain.ts` | Replace `{items}`, `{route}`, `{city}` and direct plan bodies with `{data}`; update field names, nullability, errors and bearer transport; generate transport types from OpenAPI |
| `components/auth/auth-screen.tsx`, `api/account.ts`, `api/client.ts` | Retain basic sign-up/sign-in UI but drop displayName, use 12-character creation minimum, navigate to verify/resend after registration (not authenticated), then shared login for both roles. Replace cookie/2FA handling with secure refresh storage, access bearer, non-rotating refresh, server logout and `/user/me`. Add password-change form; clear account caches/tokens on logout/change. Remove Saved/favourite flows; registration no longer implies saving features |
| Admin screens (absent) | List/edit Places, search/import, list/edit routes, select ordered Places, publish/unpublish; all required form fields are in write schemas; full admin route GET preloads the editor |

Existing fixture data lacks Poznań and generation support. Future fixtures must follow the new contract, including geometry. On startup refresh from secure storage, then read `/user/me`; on role user hide admin UI, while backend still enforces 403. Avoid parallel refresh storms and never automatically retry rejected credential operations. On a protected-request 401, try refresh once, then retry once or require login. Treat public endpoints separately: browsing/generation never require a session. Admin Place forms can save safe changes without unpublishing; on routing-change 409 explain affected-publication policy. No frontend/backend code is changed by this documentation task.

## Material assumptions to confirm during integration

Intensity ceilings remain sensible coarse MVP defaults: they are maximum walking distance, while total available time includes visits. No new fitness calculations are needed. The backend teammate must select routing/POI and email delivery providers; availability/licensing and native Mapbox compatibility require implementation checks. Token format and storage design remain backend decisions. Secure native refresh storage is required; any future persistent browser login needs a separate storage decision, without changing native transport. Supervisor approval is still needed if formal criteria mandate deferred features; see [scope mapping](../requirements/mvp-scope.md).
